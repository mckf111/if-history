> 状态：历史设计记录。主体方案已在 v0.3 落地，v0.4 的后续打磨见 [更新记录](../../CHANGELOG.md)；当前实现以 [README](../../README.md) 与 [架构说明](../ARCHITECTURE.md) 为准。

> 日期：2026-07-13  
> 基线：`main@d0aa619` 及 `docs/ADVERSARIAL-REVIEW-2026-07-13.md`  
> 实施分支：`codex/first-principles-overhaul`

## Goal

在不推倒纯函数模拟骨架的前提下，把《城破前夜》升级为一款视觉鲜明、开局有钩子、选择有回响、结局可复盘的历史实验游戏，同时补齐真实、克制、可验证的 SEO（搜索引擎优化）与 GEO（生成式引擎优化）。

## Assumptions and Boundaries

- 保留现有三日、十二时辰、三撬点与三层编年史结构，不另做第二套游戏。
- 先修审查报告中会让世界“说谎”的因果与状态问题，再做视觉和内容强化。
- 史实只做约束，不替虚构情节背书；来源必须能点开，并说明具体支撑范围。
- 所有规则继续是纯函数；随机继续只来自存档种子；React 只提交命令。
- 公开网页无法技术上保证“绝不被抄”。本次采用原创视觉、版本留证、双轨授权、版权声明与训练爬虫拒绝策略，提高追责能力和低成本照搬门槛，但不作虚假保证。
- 不引入运行时服务、账号、联网接口、第三方美术资产或新的产品功能面。

## First-principles model

一局游戏要持续回答五个问题：

1. 我是谁？——城外刻字铺的代工姚小满。
2. 我为什么现在行动？——城破倒计时只剩十二个时辰。
3. 我想保住什么？——弟弟、匠户姓名或三条胡同，开局立誓。
4. 我的选择改变了什么？——文书经过具名人物的欲望、恐惧和私心，形成可见回响。
5. 我为什么得到这个结局？——终局从文书、投递、信念、行动、支柱一路回放到结局。

若其中任一环断裂，更多文案、动效或结局都只是包装。

## Chosen approach

采用“因果闭环驱动的单线升级”。不采用两个备选方案：

- 只换皮：改动快，但会把审查报告中的因果矛盾藏在更漂亮的界面下。
- 推倒重写：会丢掉现有纯函数、种子重放与三层编年史的好骨架，风险过大。

实施顺序固定为：规则可信 → 引导与叙事 → 视觉 → 可发现性 → 全量验证。

## Experience design

### 开局

门面只做三件事：给出身份、倒计时和核心动词。新局先进入一段短促序章：远处炮声、催交牌记、弟弟的红绳结依次出现；玩家在“救春生、护匠籍、保街坊”中立下一项誓愿。誓愿不提供数值加成，只给这一局一个情绪目标，并在终局按真实撬点结果兑现或反讽。

### 白天

顶栏持续显示距城破还剩多少时辰、已用时辰和下一嫌疑阈值。当前地点只给眼前可做的动作，工作台明确说明每种文书缺什么、去哪找。每次动作从因果账派生一条短回响，不另造一套状态。

### 夜晚

夜报按“城势、你的字走到哪里、人物自己做了什么”组织。玩家只看到合理可见的信息，但能感到动作在发酵。换屏自动回到标题并播报，不继承旧滚动位置。

### 终局

三撬点组合整理为七类有辨识度的结局，再加被捕结局。结局首屏先展示标题、誓愿兑现情况、三枚撬点印和继续行动按钮；详细编年史与因果复盘放在其后。事实、记载、流传继续分层，并给史实条目直接来源。

## Visual system

视觉方向为原创“子夜档案馆”：

- 深墨夜色占主画面，暖纸作为行动岛，朱砂只标危险与不可逆选择，铜金只标时间。
- 门面使用代码绘制的木刻城墙、月轮、更鼓波纹与活字排布，不使用第三方图片。
- 版面从居中纸卡改为舞台式不对称构图；桌面保留城图与工作台并置，移动端按危机信息、行动、地图、物品排序。
- 动效只服务三个高影响时刻：进场揭幕、落刀盖印、夜幕／终局换场；遵守减少动画偏好。
- 小字与纸面正文满足可读对比度，键盘焦点清楚，模态具备标题、焦点圈闭、关闭与恢复。

## Rules and data changes

- 存档升级到 v5，增加开局誓愿、文书制作日期、世界物件移除记录和编年史来源。
- 未倒任何柱时撬点胜算为 0；有玩家因果后才进入 10% 基础加权骰。
- 确定性的世界行动（如烧册）可直接保证相应世界结果，终局不得否认。
- 流言只读夜初快照；新增信念下一夜才可继续传播。
- 完整因果链至少覆盖：采集 → 制书 → 投书 → 私心骰 → 送达 → 验看 → 信念 → 人物行动 → 支柱 → 撬点 → 编年史。
- 所有命令做严格判别联合校验：拒绝未知字段、负时辰、重复 ID、原型键和不存在的内容 ID。
- 世界物件取得、消耗、没收或烧毁后都不重生；纸料按合理份数消耗，保证主要路线可规划。
- 史鉴做深校验；免费移动达到保护阈值后仍可通过耗时动作结束游戏，不形成死档。

## SEO / GEO

- 使用描述性标题、准确摘要、规范链接、开放图谱元数据和站点名称。
- 以 `VideoGame` + `WebApplication` 的 JSON-LD 描述真实属性；不虚构评分、评论或奖项。
- 首屏与无脚本回退均提供可抓取的“游戏是什么、怎么玩、历史边界、来源、授权”正文。
- 提供 `robots.txt` 与 `sitemap.xml`。允许常规搜索与 `OAI-SearchBot`，拒绝 `GPTBot`；搜索可发现与训练授权明确分开。
- 史料、规则与授权使用稳定锚点和直接链接，使生成式答案可以引用具体段落，而不是猜测游戏内容。

依据的一手规范：Google Search Central 的摘要与结构化数据文档、Schema.org 的 `VideoGame` / `WebApplication` 定义、OpenAI 发布者与开发者爬虫说明。结构化数据只帮助理解，不承诺富媒体结果或排名。

## Success Criteria

- 零行动局不再出现“玩家促成”的撬点成功。
- 已发生的烧册／焚证等行动能被场景和终局读取。
- 同夜传播最多一跳，且人物数组顺序不改变结果。
- 任一结局可从编年史回溯到真实上游命令；所有骰值有账。
- 畸形命令与损坏史鉴均被拒绝；一次性物件不重生；移动保护阈值不造成死档。
- 键盘可完成移动和全部模态流程；桌面与 390px 移动端无横向溢出、关键信息不被旧滚动位置推走。
- 首次进入 30 秒内能理解身份、危机、目标和第一个有效动作。
- 至少七类正常结局与一类失败结局可由规则区分，终局明确反馈誓愿。
- 生产 HTML 含准确元数据、规范链接、JSON-LD、可抓取正文；`robots.txt` 与 `sitemap.xml` 路径正确。
- `npm test`、`npm run build`、依赖审计与真实浏览器桌面／移动截图复核全部通过。

## Step-by-Step Execution Plan

1. 修因果、命令与存档结构 → 验证：对抗样例与重放测试。
2. 修史料、来源与编年史 → 验证：所有撬点组合、日期、地点和来源测试。
3. 实装誓愿、引导、回响与结局族 → 验证：合法完整玩家路径与结局可达性。
4. 实装“子夜档案馆”视觉与可访问性 → 验证：键盘、焦点、对比度、桌面／移动截图。
5. 实装 SEO/GEO 与权利声明 → 验证：生产文件、结构化数据和爬虫文件检查。
6. 全量回归并分逻辑提交 → 验证：干净工作树、提交历史可读、分支不触碰 `main`。

## Final Completion Criteria

只有在代码、玩家可见文本、README、架构、史实边界、版本号、存档版本、测试与构建全部互相一致，且真实截图未发现明显视觉或移动端问题时，目标才算完成。
