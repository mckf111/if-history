# 架构说明

## 设计边界

游戏是纯前端单页应用。React 负责展示和收集 `PlayerDecision`，所有规则由 `src/game/engine.ts` 中的纯函数执行。界面不得直接修改国势、资源、人物关系或随机状态。

没有服务器、数据库或运行时内容生成。事件表、人物和来源均随构建产物发布，因此同一版本中的同一种子可以完全复现。

## 单局状态机

```text
createGame(seed)
  → 准备回合：主线事件 + 从本幕事件池抽取一个未见事件
  → 处理主线奏案：政策 + 可选执行者
  → 处理局势奏案：政策 + 可选执行者
  → 回合推进：结算到期命令、更新国势、抽取下一回合
  → 第十二回合结束：buildEnding(state)
```

`GameState` 是唯一权威状态，包含：

- `turn`、`act`、当前奏案和本局已见动态事件。
- 五项 `metrics` 与内帑、驿骑两项 `resources`。
- 人物存亡、关系、剧情旗标和等待结算的命令。
- 随机数内部状态、玩家决策记录和可公开回报。
- `saveVersion: 1`。结构变动必须升级版本并增加迁移或明确拒绝旧存档。

## 决策与延迟执行

政策可以包含三类后果：

1. `cost`：落印时扣除的明确资源；不足时不能选择。
2. `immediate`：立即发生的确定性状态变化。
3. `check`：延迟 1–2 回合的执行判定，保存事件、政策和执行者引用。

判定到期时才使用当时国势计算胜算：

```text
胜算 = 基础胜算
     + Σ((国势 - 50) × 对应权重)
     + (执行者能力 - 10)
     + 人物关系 × 0.2
```

结果限制在 10%–90%。游戏过程只显示四档风险，结局页公开精确胜算与掷值。

随机数使用存档内的 32 位线性同余状态：

```text
next = (state × 1664525 + 1013904223) mod 2³²
```

禁止在规则代码中使用 `Math.random()`。新局种子可由当前时间产生，但之后所有抽取和判定都只依赖 `rngState`。

## 内容模型

每个 `EventDefinition` 必须包含：

- 唯一事件 ID、所属幕、时间、分类、奏报和策略背景。
- 一个来源 ID，以及明确区分史实和架空部分的 `boundary`。
- 恰好三个 `ChoiceDefinition`；选择不能只换措辞而没有不同代价。

`validateContent()` 在测试中检查事件 ID、选择 ID、人物引用、延迟和每幕事件池容量。新增事件时必须保持十二个主线事件，并让每幕至少有五个动态事件。

## 结局

`buildEnding()` 先依据国势和关键制度旗标选择六类国运之一，再拼接三段长期叙事：民间承受、制度遗产、北方关系。结局优先级避免低粮但已有海上退路的局面被误判为普通朝局崩溃。

结局不是线性总分：例如高合法性但低兵权会进入“军镇挟天子”，而不是用平均值抵消指挥链崩坏。

## 存档与隐私

- `localStorage` 保存一个 `what-if-history.autosave.v1` 自动存档。
- 完成的结局写入 `what-if-history.annals.v1`，相同种子和结局不重复，最多保留 20 条。
- 所有数据仅留在当前浏览器，不上传任何信息。
- 每次落印后立即保存，包括随机状态和待结算命令。

## 验证

`npm test` 覆盖内容完整性、完整十二回合、同种子复现、序列化复现、资源与执行者校验、六类结局和损坏存档。

`npm run build` 同时执行 TypeScript 项目检查和 Vite 生产构建。界面变动还应在 1440×900 与 390×844 视口各完成一次真实浏览器检查。
